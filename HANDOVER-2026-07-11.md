## Why this is urgent, not cosmetic

The viewer treated a kind:5 `a`-tag deletion as a **permanent tombstone on the
coordinate**: any matching kind:31237 was dropped regardless of timestamp.

But an `a` tag names a *coordinate* — `kind:pubkey:d` — and that coordinate is
**reused every time a release is republished**. So an unpublish → republish
cycle produces a new, valid event that the viewer discarded on sight.

This week ndisc's library was bulk-unpublished and then republished. That leaves
a kind:5 in the history of **every coordinate**. So the bug does not hide a
stale release or two — as the deletion subscription catches up, the viewer drops
the **entire catalogue**.

(This also explains an earlier red herring: ~136 releases still appearing after
an unpublish. That was never "relays honouring kind:5 inconsistently" — it was
glmps having received only a partial slice of the deletion events.)

**The fix:** strict NIP-09. Keep the newest deletion timestamp per coordinate;
kill only events with `created_at <= deletion.created_at`. `e`-tag deletions
stay permanent — they name one content-addressed event id, which is never
reused.

Three read paths had it, all fixed:

| file | what it broke |
|---|---|
| `src/hooks/useReleases.ts` | the catalogue — would have emptied |
| `src/hooks/useReleaseByAddr.ts` | the single-release page — 404 on republished releases |
| `src/lib/feed.ts` | kind:31239 notes — identical bare-`Set` tombstone; any republished note invisible |

## Publisher side — ndisc v0.1.4-beta.5 (`16324ef`, pushed)

No contract change. `release.v2` is untouched and its SHA is unmoved
(`91e16cf1…`), so **nothing to re-vendor and no schema:check implications.**
Every new column is local-only, never emitted.

What changed that matters to a reader:

- **Deletions now carry `e` + `a`.** ndisc stores the live event id
  (`last_published_event_id`) and names it on retraction. `a`-only deletion is a
  **no-op on nostr-rs-relay**, which `relay.fizx.uk` runs — it honours NIP-09 by
  event id only. Every unpublish ever sent to fizx had been stored and never
  applied: 2,528 inert kind:5 events while it still served 770 retracted
  releases.
- **Four-state publish lifecycle** (`never` / `published` / `stale` /
  `retracted`) replacing the overloaded `last_published_at IS NULL` test.
- **"Reconcile relays"** — audits each relay against the DB (ok / ghosts /
  orphans / absent / stale) and purges strays, recovering event ids from the
  relay itself. That last part is the only way to reach *orphans*: events whose
  local row vanished in a DB rebuild, so nothing local can ever drive their
  deletion.

ndisc had **the same tombstone bug** in `reconcile_published` (it collected `a`
tags into a bare id set), plus a relay-pagination bug worth knowing about
generally:

> Paginating a relay with `until = oldest - 1` **silently drops events**. A bulk
> publish stamps hundreds of events with the same `created_at`; if a 500-event
> page boundary lands mid-second, everything left in that second is skipped. Step
> to `oldest` **inclusive** and dedupe by id — overlap is free, a gap is
> invisible and corrupts every diff computed from it.

### The relay set — please keep this invariant

`DEFAULT_RELAYS` in `src/config.ts` is **fizx + nos.lol + primal** on both forks,
and ndisc is configured with the same three.

> **ndisc's relay list must be a superset of whatever the sites read.** ndisc
> only sends publishes and deletions to its *own* relays. Add a relay to a glmps
> config without adding it to ndisc, and deletions never reach it — the site goes
> on showing releases that were unpublished.

**Primal is intentionally sparse (22 of 1,728).** It was never configured during
the publish runs. The decision is to *leave it that way*: keep it in the list so
deletions still reach it and its 22 stay in sync, but do **not** bulk-publish the
library to it — it stores-but-ignores kind:5, so that would seed a third ghost
farm. Readers union their relay set, so fizx + nos.lol already cover everything.
Nothing to do here; just don't "fix" it.
